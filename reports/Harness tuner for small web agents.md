# An honest scoreboard beats clever search

The best tuner for Errand is a strict judge wrapped around a simple searcher. Most of its work is deciding honestly whether a change really helped, not inventing clever changes. (The "harness" is everything around the brain: the page view it reads, the form it fills, the rules that snap its answers to the page, its examples and its settings.) Your test set of 190 answers can reliably notice only gains of about **5 points or more**. After 30 tries, the luckiest variant looks **4–6 points better than it really is**, so a tuner that simply keeps the top scorer will mostly be keeping luck (my calculation from [Miller](https://arxiv.org/pdf/2411.00640)'s formulas). Published results show how badly this goes on small sets. One prompt optimizer trained on 30 examples lost **28 points** on new questions ([MAGE](https://arxiv.org/pdf/2607.11944)). On Qwen3.5-2B itself, an optimizer guided by GPT-5.4 still finished **9 points below** a good hand-written prompt ([guarded routing study](https://arxiv.org/html/2607.24801)). So the tuner should lock 12 of the 40 pages in a "vault" it never tunes on, measure how much scores wobble by pure chance before it starts, search the big knobs first (what the brain sees and what form it fills, the knobs that took you from 39% to 96%), drop losing variants after a few pages, and accept a change only when it clearly wins on the same questions and makes up no new answers on the "none" questions. It should keep one shared harness for all four sites and allow site-only changes only for big wins. Claude Code gets called only after three rounds with no real progress, with a written list of what went wrong and a request for two small new knob settings, and the brains never rewrite their own instructions, because small models tuning their own prompts lost 4–6 points ([POaaS](https://aclanthology.org/2026.fever-1.2.pdf)). Clicks should follow the same "copy, don't count" rule that gave you 96%: the brain copies a link's words from a short list, code finds the link, and code checks that the page really changed. Speed knobs come last and stay only if accuracy holds, and every graded answer the tuner produces also helps set the "ask the human" line. The biggest single upgrade is cheap: more labelled pages, especially more "none" questions, because labels run out long before computer time does.

## Ten tuner parts, ranked by how much they protect accuracy

The ranking puts first the parts without which every later number is untrustworthy, then the parts with the largest measured effect. "Noise" means the wobble in a score that comes from luck rather than from the change being tested. "Paired" means two variants are compared on exactly the same questions, so you can count which answers each one fixed or broke.

| Rank | What to build (plain words) | The numbers behind it | Cost on your laptop | Helps |

For changes meant for every site, tune on 3 sites and test on the 4th | Four harness-tuning methods all gained on their practice set. Use graded runs to set the ask-line | The grammar-limited form slowed each decode step from **194 to 344 ms** ([Errand logs](../bench/server-np53-point.log)). Calibrated ask-lines cut help requests by **10–24%** ([KnowNo](https://arxiv.org/html/2307.01928v2)) | Config changes and a log | Speed, fewer asks |

Two popular choices should be skipped. Do not run a ready-made optimizer such as GEPA or MIPROv2 end to end. Their budgets are built for validation sets of about 300 items ([GEPA](https://arxiv.org/html/2507.19457)), and on the one published 2B test neither GEPA nor examples beat the hand-written prompt ([guarded routing study](https://arxiv.org/html/2607.24801)). Borrow their best parts instead: written failure feedback, cheap screening and keeping variants that win on some pages. And do not let the 53 brains vote on, debate or write harness edits. Proposals come from the knob menu in code or from Claude.

## Your 190 answers can only see gains bigger than five points

Think of the tuner as a contest between versions of the harness on a practice test. With a small test, luck decides close contests. If a harness gets 171 of 190 answers right (90%), its true accuracy could reasonably be anywhere from **84.9% to 93.5%** (a "Wilson interval", the method recommended for small evaluations over the textbook formula, which "usually dramatically" underestimates uncertainty below a few hundred items) ([Bowyer et al.](https://arxiv.org/pdf/2503.01747)). The real spread is wider still. Answers from one page share one page view, so they tend to be right or wrong together. In reading tests with several questions per passage, the honest error bars came out up to **3 times** wider than the naive ones ([Miller](https://arxiv.org/pdf/2411.00640)). So the tuner should resample whole pages, never single answers, when it estimates how sure it is.

The fix is to compare variants **paired**, on the same answers, and count only the answers where they disagree. Under an exact test (McNemar), a variant that fixes 6 answers and breaks none is a real win (p = 0.031; p is the chance that luck alone would give a result this lopsided, and under 0.05 is the usual bar for "real"). Fixing 7 and breaking 1 is not yet proof (p = 0.070), and neither is 9 fixed and 2 broken (p = 0.065). Eight fixed and 1 broken just passes (p = 0.039). In practice a change needs a net gain of about 6–8 answers, or 3–4 points, with almost no new errors (my calculation). The table below shows the smallest gain each slice of your data can reliably detect, assuming the two variants disagree on 5–10% of answers. It uses Miller's power formula at the usual settings (80% power, 5% false alarms), with my own arithmetic.

| Slice of the test set | Answers | Smallest gain it can reliably see |
|---|---|---|
| Whole set | 190 | 4.5–6.4 points |
| Tune pool (28 pages, after locking the vault) | about 133 | 5.4–7.7 points |
| Vault (12 pages) | about 57 | 8.3–11.7 points |
| One site (10 pages) | about 48 | 9.0–12.8 points |
| Doubled set (80 pages) | 380 | 3.2–4.5 points |
| "None" questions | 7 | 7 of 7 right still allows a true rate as low as 64.6% |

Trying many variants makes this worse, which is the trap called the "winner's curse". If 30 variants are all secretly equal, the best-looking one is expected to beat the others by about **4.2–6.0 points** on 190 answers by luck alone (calculated as the noise times √(2 ln 30)). So a variant that tops a 30-way scoreboard by 3–4 points is fully consistent with pure noise. Published work shows the trap in action. RRSI compared four 2026 methods that evolve agent harnesses. Every one gained on its practice set, for example Meta-Harness going from 89.4 to 93.0. Their scores on fresh tasks of the same kind were "quite similar" (88.5–89.2) and could not tell the methods apart. Only tasks from different benchmarks revealed the overfitting, and there "the ranking inverts" ([RRSI](https://arxiv.org/pdf/2609.24972)). Overfitting means memorising the practice test instead of learning the skill. MAGE found that GEPA with 30 training examples scored **34.0% against 62.4%** for the prompt it started from, because "each example represents 3.3% of the signal" and a few clustered failures steered the prompt into a narrow strategy ([MAGE](https://arxiv.org/pdf/2607.11944)). Each of your pages carries about 4.75 answers, so one odd page template can steer a tuner in exactly this way.

The server adds its own wobble. Even at temperature 0, results change with how requests are batched together. That is why Qwen3-235B gave 80 different completions in 1,000 runs with normal kernels ([Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/), via [Spheron](https://www.spheron.network/blog/vllm-batch-invariance-why-temperature-0-isnt-deterministic/)). llama.cpp warns that cached results "are **not** guaranteed to be bit-for-bit identical" across batch sizes ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). So before any tuning, run the current harness 3–5 times, once with 1 brain and once with all 53 sharing the GPU. Set the noise band (call it ε) to the biggest spread you see, and score any answer that flips as the average of 3 runs. RRSI measured its noise band the same way, by repeating the unchanged harness 3–5 times. It calls the band "the one value that must not be tuned, since lowering it buys evolve-set score on noise alone" ([RRSI](https://arxiv.org/pdf/2609.24972)). Also run the current harness alongside every candidate in the same session, so a server or page-cache change cannot pose as an improvement. RRSI reports every number against a baseline "measured in the same window" for this reason ([RRSI](https://arxiv.org/pdf/2609.24972)).

The split that follows from this is simple. Put 1 page per template from each site in a **vault**: about 3 pages per site, 12 pages and about 57 answers. Score the vault only on the final winner of a tuning cycle, log the result, and report the vault score as the harness's real accuracy. If the winner fails the vault, do not re-tune against it. Swap fresh pages into the vault next cycle instead. This is the reusable-holdout discipline of Dwork and colleagues, who showed that reusing a holdout adaptively leaks information each time ([Dwork et al.](https://arxiv.org/abs/1506.02629)). The other 28 pages form the **tune pool**, split by page into 4 groups that take turns being the test group, so ideas are judged on pages the proposer did not study. For any change meant for all sites, add **leave-one-site-out** testing: tune on 3 sites, score on the 4th, and rotate. It is the nearest thing you have to RRSI's "different benchmark" check, the only check that caught overfitting there.

What gets counted matters as much as how. Score "none" questions in their own columns: answers made up where the truth is "none", and false "none" where an answer exists. Allow **zero** new made-up answers against the current harness. Errand's own logs show why the false-"none" column matters: with "null" allowed, brains answered null for every field on **69 of 105 pages** ([Errand bench](../bench/results.md)). Seven "none" questions only catch disasters. Adding 1–2 questions per page about fields that truly do not exist would reach about 35, and 33 of 35 right would pin the true rate to **81.4–98.4%** (calculated). Before comparing answers, normalise both sides by type: prices as decimals, dates as ISO, whitespace collapsed, and "N/A", "not found" and empty all mapped to one NONE value. Keep the normaliser under version control, because changing it can move scores with no harness change at all. Treat partial credit as a diagnostic only. A near-miss price is still a wrong errand. Tools that sort answers into "abstained, answered, fabricated" follow the same three-way logic ([deepeval](https://deepeval.com/docs/classifiers-abstention)).

## Big knobs first, one at a time, with losers dropped early

The knobs that change what the brain sees and how it answers are worth far more than fine-tuning wording or sampling. Small formatting changes in prompts swung LLaMA-2-13B by up to **76 points**, and how well a format works "correlates only weakly between models" ([FormatSpread](https://arxiv.org/html/2310.11324v2)). Any format idea, including Claude's, must therefore be scored on Qwen3.5-2B at your real Q4_K_M setting, not borrowed from big-model results. Cleaning only the page view and the action list lifted a web agent **26.6 points** with no examples or prompt tricks ([AgentOccam](https://arxiv.org/html/2410.13825v1)). Your own runs fit the pattern. Line-number answers scored 39%, line numbers without "null" scored 64%, and writing the value while code snaps it to its page piece scored 96% ([Errand bench](../bench/results.md)). That was measured on 35 pages of one site, but a 57-point gap dwarfs any noise band. The menu should be searched in this order:

| Order | Knob family | Values worth trying | Why it sits here |
|---|---|---|---|
| 1 | Page view | which labels to keep, how pieces are cut, page headings shown as context, trimming rules | Largest measured effects ([FormatSpread](https://arxiv.org/html/2310.11324v2), [AgentOccam](https://arxiv.org/html/2410.13825v1)) |
| 2 | Answer form | write value and snap (current); evidence field first or last; strict form on or off with a lenient code parser; "none" allowed or not | 39% vs 64% vs 96% ([Errand bench](../bench/results.md)) |
| 3 | Snap rules | whole numbers only; prefer the main content over "you might also like" lists; reject values ending in "..." | The stock number 18 once snapped to "£44.18", and most rating misses came from another book's stars lower on the page ([Errand bench](../bench/results.md)) |
| 4 | Examples | 0, 1 or 2 solved pages of the same template; answer-only examples | Examples cut Qwen3.5-2B from **90.58 to 70.43** in one study ([guarded routing study](https://arxiv.org/html/2607.24801)), so "zero examples" must always stay on the menu |
| 5 | Sampling | temperature 0 vs low temperature with a 3-way vote on failing fields only; presence penalty 0 | Qwen's suggested settings (temperature 1.0, presence penalty 2.0) are for chat ([Qwen3.5-2B card](https://huggingface.co/Qwen/Qwen3.5-2B)). Voting on everything would cut throughput about threefold |

The search itself should be plain. A 2025 study of a 162-setting space found that about **10 tries matched the best setting a full grid found**. Bayesian search (TPE) did no better than random tries, and changing the most important knob first reached a top setting in as few as **3 tries** ([RAG tuning study](https://arxiv.org/html/2505.03452v3)). So first sweep each knob family one at a time around the current best, in the order above. Then try a small random batch that combines the best values of the top two or three families. Then **race**. Score every candidate on 5 pages, drop those clearly worse, add pages (10, then 20, then all 28), and stop when one survivor remains. Racing methods (F-Race, irace) do exactly this, discarding candidates "as soon as statistically sufficient evidence is gathered against them" ([irace](https://www.rdocumentation.org/packages/irace/versions/4.4.0/topics/irace_cmdline)). With about 5 evaluations per candidate, sequential halving beat equal spending by about 15%, and the advantage disappeared at about 30 evaluations per candidate ([TRIPLE](https://arxiv.org/html/2402.09723v3)). A two-day-old preprint supports the same shape from another angle. Generating up to 100 candidates using only 3-item test batches and then fully checking just 20 beat a GEPA variant in 8–9 of 10 comparisons ([Explore More, Validate Less](https://arxiv.org/html/2610.27367)). It is unreviewed, with three seeds and no significance tests. One GEPA idea is worth copying for picking what to try next. Keep any variant that is best on at least one page, not only the best on average. That "Pareto" choice gained **12.44 points against 6.05** for always building on the top scorer ([GEPA](https://arxiv.org/html/2507.19457)). Use it to choose which variant to change next, never to crown a winner. Skip GEPA's "merge" step, which cut one small-model task by 10.38 points ([GEPA](https://arxiv.org/html/2507.19457)).

The acceptance rule, which crowns winners, should work like a row of gates that must all open. First comes a leakage screen, before any scoring. Reject any change that contains an answer value, a page's own text or, for a global harness, a site's name. RRSI's critic rejects edits that encode "task names, entity names, task-specific values, answers". Screening first means a leaking candidate never gets an inflated score that attracts later rounds ([RRSI](https://arxiv.org/pdf/2609.24972)). Second, the paired page-level test on the tune pool must show a real gain. Because many variants are tried per cycle, require the gain to exceed ε plus about 3 points. Third, there must be no new made-up answers on "none" questions. Fourth, the vault score must be no worse than the current harness's by more than ε. When two variants are within ε and the paired test finds no difference, call it a tie. The faster one may then win, but only if its accuracy is at worst 1 point lower, measured by the lower end of its interval. Otherwise the current harness stays. The incumbent is the default, in the spirit of the "Ladder" rule, which posts a new best only when it beats the old one by a margin ([Blum & Hardt](https://arxiv.org/abs/1502.04585)).

Add RRSI's two guards against slow decay. A "stability floor" never accepts a score below the best so far minus ε, which stops "walking downhill through a sequence of regressions that are individually small enough to be mistaken for noise". A cost rule makes extra prompt length earn its keep. RRSI's version of these rules ended with a harness that used **30% fewer tokens** ([RRSI](https://arxiv.org/pdf/2609.24972)). Length matters doubly for a 2B brain with a 4,096-token slot. Prompt optimizers without a length cap added "thousands of extra prompt tokens" and lowered small-model accuracy, while a minimal-edit method with strict length limits gained **+2.3 points** on a 3B model ([POaaS](https://aclanthology.org/2026.fever-1.2.pdf)). Finally, limit edits per candidate: up to 3–4 early in a cycle, down to 1 late in the cycle. A single change can then be credited or blamed, which is what makes a lesson trustworthy ([RRSI](https://arxiv.org/pdf/2609.24972)).

A per-site harness sounds smarter, but the data cannot support it. Each site has about 48 answers, which can detect only gains of 9–13 points (calculated). Tuning per site multiplies the number of choices while shrinking the evidence behind each one, the very setting where MAGE's optimizer narrowed onto clustered failures ([MAGE](https://arxiv.org/pdf/2607.11944)). Tune one global harness with leave-one-site-out checks. Let each site try a few "global plus one local edit" variants, and accept one only if it beats the global harness by at least 8 points (or ε, if larger) on that site's held-out pages. Per-template knowledge belongs in code rules that can be checked, such as selectors, verified on at least 2 held-out pages. Your recipe path already does this, and replayed recipes scored 100% on books.toscrape ([Errand bench](../bench/results.md)). Free-form prompt rewrites per template should not be allowed.

None of this is expensive in computer time. Reading tests use cached pages, so they need no browser windows. At the measured 1.6 pages per second in point mode ([Errand bench](../bench/results.md)), a full 40-page pass takes about 25 seconds. Three repeats take about 75 seconds, and 50 variants about an hour, less with racing (calculated). That means the scarce resource is labelled answers, not brain time. More tries only raise the luck boost, which grows slowly with the number of variants: about 3.5 points at 10 tries and about 4.5 at 50, with 5% of answers disagreeing (calculated). That is why the tuner must count its "looks" at the data and respect the margin rule.

## Claude Code gets called on stalls, with a failure report, never the vault

Ideas must come from code or from a stronger model, never from the brains themselves. When the same small model wrote its own prompt improvements, Llama-3.2-3B fell from **63.7 to 59.8** with EvoPrompt and to **57.5** with OPRO, and factual accuracy dropped too ([POaaS](https://aclanthology.org/2026.fever-1.2.pdf)). A strong idea-writer helps. In ACE, a GPT-OSS-120B reviewer lifted a finance task from 70.7 to 76.6, and GPT-5.1 lifted it to 78.5 ([ACE](https://arxiv.org/pdf/2510.04618)). But even a strong writer guarantees nothing on a 2B brain: GEPA guided by GPT-5.4 scored 81.61 on Qwen3.5-2B against the hand prompt's 90.58 ([guarded routing study](https://arxiv.org/html/2607.24801)). So Claude's ideas enter the race as ordinary candidates and pass the same gates.

Call Claude only when the search stalls, which RRSI defines as three rounds in which progress stays inside the noise band ([RRSI](https://arxiv.org/pdf/2609.24972)). That keeps the call count low. GEPA-style tuning makes roughly one reflection call per iteration, which comes to an estimated 30–80 strong-model calls for 300–500 test runs. That is too many for a limited subscription if Claude writes every one. Stall-only calls should come to a handful per tuning cycle (my estimate).

Each call should carry a written failure report, because the words explain what a score cannot. GEPA's authors name the text feedback as the main learning signal. Without it, the system falls back to the empty message "This trajectory got a score of {score}" ([GEPA](https://arxiv.org/html/2507.19457)). Errand's grader can write this report for free. For each wrong answer it can list the field, the true value, the brain's value, the page piece it pointed to and whether the snap moved it, with failures grouped by kind. Add the list of ideas already rejected, so Claude does not re-propose them. Only tune-pool pages go in. The vault never does. Ask for two proposals, following Harness²: one general change (how the page is shown, how answers are formed) and one site-specific change. Each should be written as new knob values or a small checkable code rule, under the prompt-length cap. Harness² used Claude Opus 4.8 to write such paired edits and gained **3.0 to 11.5 points** on one benchmark ([Harness²](https://arxiv.org/html/2610.14224v1)). Its own ablation shows the risk of editing without evidence: refining with no reference runs, test probes or library dropped one score from **73.4 to 63.2** ([Harness²](https://arxiv.org/html/2610.14224v1)). Harness² never sees the true answers while it refines, so it can only compare behaviour. Errand has an exact grader, so "probe and score" is a stronger check than anything Harness² could run.

Lessons belong in a ledger the tuner keeps, not in a long note pasted into the brain's prompt. RRSI logs every candidate's idea, change, score, cost and accept-or-reject decision, and notes that "rejected mechanisms remain negative evidence". Parts with no measured gain over 4–5 rounds become deletion targets ([RRSI](https://arxiv.org/pdf/2609.24972)). Store short rules, not raw run transcripts. On tasks the baseline could not solve, a memory of raw runs changed success by **−26.1 points**, while short abstract insights gave **+3.3** ([Hu et al.](https://arxiv.org/html/2604.27003v1)). Edit lessons one entry at a time and never rewrite the whole store. In ACE, one full rewrite shrank a context from 18,282 tokens to 122 and dropped accuracy from **66.7 to 57.1**, below the starting point. ACE's fix was itemised entries with helpful and harmful counters ([ACE](https://arxiv.org/html/2510.04618)). A good entry would read like "prices on listing pages can include a struck-out old price; take the other one". It names its scope (global, site or template), the pages it fixed and broke, its measured gain with an interval, a status (active, probation or retired), the date and the model. Harness² keeps a similar library of winning harnesses, each with an EXPERIENCE file, and removing that library cost it 1.8–3.1 points ([Harness²](https://arxiv.org/html/2610.14224v1)). A lesson can reach the brain's prompt only as a knob that wins its own on/off race. Track its effect separately on answers that used to fail, because Hu et al. found that average scores hide large losses on hard cases ([Hu et al.](https://arxiv.org/html/2604.27003v1)).

## Clicks copy the words and let code find the link

Published click accuracy for small models is modest, and it comes only from models trained for the job. On Mind2Web, trained models from 220M to 3B parameters chose the right element **43.6–55.1%** of the time on sites seen in training, and less on new ones ([Mind2Web](https://arxiv.org/html/2306.06070v3)). A 1.7B text agent went from **11.5% to 56.9%** task success only after training ([InSTA](https://arxiv.org/html/2502.06776v2)). Your untrained 2B brain will start lower, so the harness has to carry the weight. The best clue comes from SeeAct's comparison. Having the model describe its target in words and letting simple code search for it scored **16.1%**. Choosing from a numbered list scored **39.1%**. A human finding the element from the model's own description scored **61.9%**, so the descriptions were good and the weak code matcher was the problem ([SeeAct](https://arxiv.org/html/2401.01614)). Free-form actions were also invalid or made up **34%** of the time, against **2%** when the model picked from listed IDs ([Why do LLM web agents fail?](https://arxiv.org/html/2603.14248v2)).

Errand can combine the strengths of both and repeat its reading win. Code builds a short list of allowed links. It keeps visible, navigation-only elements and ranks them by word overlap with the goal, because long inputs make weaker models invent element IDs, and on enterprise web pages a full accessibility tree averaged **6,720 tokens** per step, more than a whole 4,096-token slot ([Read More, Think More](https://arxiv.org/html/2604.01535)). Each line looks like `[17] link "Next" -> /catalogue/page-2.html`. Repeated labels get context the brain can copy too, like `"Read more" (in: "A Light in the Attic")`, because models facing identical choices "tend to pick the first matching choice" ([SeeAct](https://arxiv.org/html/2401.01614)). The brain copies the link's words. A grammar restricts its answer to exactly one of the listed strings, so it cannot invent a target ([llama.cpp grammars](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)). Code then finds the element with Playwright's role-and-name or text locators, which throw an error when more than one element matches instead of guessing ([Playwright locators](https://playwright.dev/docs/locators)). The ID serves only as a tie-breaker, and any disagreement between ID and text is logged for the tuner. Click knobs for the menu include list length (10, 20 or 50), showing all choices at once or in groups of 5 plus "none of these" as Mind2Web does ([Mind2Web](https://arxiv.org/html/2306.06070v3)), showing the link address or not, and shuffling the order between runs. Shuffling matters because models favour certain answer positions ([PriDe](https://arxiv.org/abs/2309.03882)).

Safety and success checks belong in code, never in the brain. Before the list is shown, code removes submit buttons, buttons in forms that send data, anything whose text or label matches login, sign in, checkout, pay, post, send, subscribe or captcha, and links that log out or open carts. Playwright's normal click already refuses elements that are hidden, moving, disabled or covered by another element ([Playwright actionability](https://playwright.dev/docs/actionability)). Never use `force`. A "covered" error is a free signal that a banner is in the way, and code should decline it. After each click, code checks the expected effect: the address changed to the link's target, the page fragment changed, a tab's "selected" mark flipped, or the item count rose after "load more". The check is worth having. In one 2026 study, **34.2% of agent actions changed nothing on the page**, and **10.4%** of failures were the same action repeated more than three times ([Why do LLM web agents fail?](https://arxiv.org/html/2603.14248v2)). On "no change", retry once after the page settles, then offer the list again without the failed link. Never repeat an identical click more than twice, and hand the problem to the huddle after that. Once a path works, save each step as a role-and-name or address locator and replay it in code at zero tokens, calling the brain only for a step that fails its check. Browser Use's replay tool admits its model fallback is "really bad" ([workflow-use](https://cdn.jsdelivr.net/gh/browser-use/workflow-use@main/README.md)). Errand's code checks are what make the repair judgeable. Measure replay with token counts, because one study found that a plain agent given the same token budget "matches or surpasses" three workflow-memory methods ([budget-matched study](https://arxiv.org/abs/2606.15017)).

The click test set should score itself with code, no judge needed. Each item holds a start page, a goal, the expected effect (an exact address, an address prefix, a count increase, a tab selected or text present), the correct target and a maximum number of clicks. Cover each site's real navigation. On books.toscrape that means a category, "next" pages, opening a book by title and the breadcrumb back. On quotes.toscrape it means tag links, "Next" and author pages. On webscraper.io it means categories, links-based pagination and the "load more" page, where the address stays the same, so the check is the item count ([webscraper.io test sites](https://webscraper.io/test-sites)). On Wikipedia it means article links, the Talk and View history tabs, contents anchors and disambiguation pages, which make a good stress test for repeated link text. Add a hard slice too: repeated labels, targets below the fold and targets behind banners. Score each item four ways: the right element chosen, the expected effect seen, an invalid answer, and a click that changed nothing. Log seconds and tokens as well. To see 5-point gains as clearly as the reading set does, the click set needs roughly **150 click steps** (calculated with the same formula). It can be cheap to run. Score the choice step offline on saved candidate lists, with no windows and no web traffic, and run live checks in the 25 windows only for finalists, at your usual pace of one request every 2–3 seconds per site. Accept every valid route to a goal, not just one. Human review of a well-known web benchmark recovered **5.45–8.49 points** of real successes that the automatic checker had marked as failures ([Auditing WebArena-Lite](https://arxiv.org/html/2610.01491)).

## Speed knobs and the ask-line come last, in that order

Speed matters less than it looks, because the recipe path removes most brain work. Recipes built from 5 pointed pages replayed on all 105 pages in **0.63 seconds** with no AI, so brains run only on sample pages and on pages whose checks fail ([Errand bench](../bench/results.md)). Brain speed mostly sets how fast tuning and recipe-building go. Point mode did cost real speed, dropping from 2.66 to 1.6 pages per second ([Errand bench](../bench/results.md)). Errand's logs show why. The median decode step per slot rose from **194 to 344 ms** with the strict form, and prompts doubled from about 640 to 1,250 tokens ([plain log](../bench/server-np53.log), [form log](../bench/server-np53-point.log)). Form-checking runs on one CPU thread, slot after slot, and it switches off sampling on the graphics card ([llama.cpp sampling code](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11718/common/sampling.cpp)). Tune speed separately, after accuracy. Keep a speed setting only if accuracy drops by no more than 1 point and the gain holds across 3 repeats, with job counts that are multiples of the slot count, because uneven counts distorted earlier 70- and 80-slot results ([Errand benchmark](Maximum%20parallel%20brains%20on%20laptop%20GPU.md)).

| Speed knob | Now | Try | Why |
|---|---|---|---|
| Answer form | strict JSON form | plain output with a code parser, or a flat form | 194 vs 344 ms per step ([Errand logs](../bench/server-np53-point.log)). The form also blocks GPU sampling. Note that forms can silently fail open and produce unconstrained output ([issue #19051](https://github.com/ggml-org/llama.cpp/issues/19051)), so log the valid-answer rate either way |
| Thinking switch | `--reasoning-budget 0` | `-rea off` | Any reasoning budget turns off GPU sampling ([llama.cpp sampling code](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11718/common/sampling.cpp)). Check outputs for stray `<think>` tags ([issue #20182](https://github.com/ggml-org/llama.cpp/issues/20182)) |
| Saved checkpoints per slot (`-ctxcp`) | 2 | 3 or 4 | The shared start of the prompt was reused on only **2 of 105** tasks, because the checkpoint holding it was thrown out ([Errand logs](../bench/server-np53-point.log), [server code](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11718/tools/server/server-context.cpp)). Each extra checkpoint costs about 1 GiB across 53 slots |
| Prompt layout | about 99 shared tokens | all fixed instructions first, page last | If 800 of 1,250 tokens were shared, reuse would save about 0.15 s per page (calculated) |
| Batch size (`-ub`) | 512 | 1024 | **+4%** prompt speed measured on this laptop ([Errand benchmark](Maximum%20parallel%20brains%20on%20laptop%20GPU.md)) |
| Memory cache type | q8_0 | keep q8_0 | 4-bit cache showed 3–4 times more drift than 8-bit on Qwen models ([localbench](https://localbench.substack.com/p/kv-cache-quantization-benchmark)) |
| Speculative decoding | off | keep off | Your model file has no MTP head (checked locally), and parallel use is "not fully optimized yet" ([PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)) |

The four goals rank like this, as my recommendation: a wrong answer that slips through costs you the most, an ask costs you a minute, and a slow page costs a second. So the tuner should first fix an error target (say, at most 2% wrong among answers accepted without you), then keep asks as low as possible, then go for speed. The tuner's graded runs supply the data for this. Each graded answer records its warning signals: whether the value snapped to a piece exactly, whether independent brains agreed, and the lowest probability among the answer's own word-pieces. llama-server can return those probabilities through `logprobs` in this build ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). With these points, pick the lowest line at which the worst-case error among auto-accepted answers stays under the target, and send everything below the line to you. KnowNo set its ask-line this way and cut human help by **10–24%** at the same success rate ([KnowNo](https://arxiv.org/html/2307.01928v2)). DeepMind's version keeps made-up answers under a chosen rate ([conformal abstention](https://arxiv.org/abs/2405.01563v1)). Set the line on the tune pool, check it on the vault, and add "asks per 100 pages" to the scoreboard. Every answer you give later becomes a new labelled test item. Each ask therefore grows the test set and sharpens the line.

Last, guard what has been won. Keep 1–2 live "canary" pages per site with known answers, each with a fingerprint of its page layout, and run them daily and before big jobs. If a canary drops by more than ε twice in a row while its layout fingerprint is unchanged, the harness got worse, so roll back. If the fingerprint changed, the site changed, so re-tune that site only. Give every promoted harness an ID that stores its vault score, its ε, the code version and the model file. Rolling back then means pointing at an older ID. Re-measure ε whenever the model, its quantization or llama.cpp changes, since all three change the noise. Open-source tools can block a change in CI when scores drop and post a table of differences ([evalgate](https://github.com/AgentPostmortem/Evalgate)). No source gave canary schedules or rollback thresholds for web agents, so these numbers are my suggestions.

## Conclusion

The tuner's main job is to say "no". On books.toscrape the big structural wins are already banked: snapping lifted reading from 39% to 96%, and recipes reached 100%. The other three sites may still hide big wins of that kind, and only the first baseline runs will show it. Once those are found, the gains left will mostly be a few points each, below what 190 answers can see. That changes where effort pays. An hour of laptop time buys about 50 variants, while an hour spent labelling pages and adding "none" questions changes what the tuner can see at all. Doubling the answers shrinks the visible gain from 4.5 to 3.2 points, which no search method can do. Feeding your own answers to stuck problems back in as test items turns the human-ask stream into the test set's growth engine.

The one place a big jump is still likely is clicks, because the "copy the words, code finds the target" idea has not yet been measured there. SeeAct's gap between a weak matcher (16%) and a human matcher (62%) suggests that good code matching on text-rich practice sites could recover much of the difference, but that is a reasoned bet. No one has published a zero-shot 2B click-accuracy number, so Errand's click set will be the first. Several key sources here (RRSI, Harness², "Explore More, Validate Less", MAGE) are unreviewed 2026 preprints, and almost none of the evidence comes from brains as small as yours. Treat the ranking as a starting plan that the vault confirms or overturns.
